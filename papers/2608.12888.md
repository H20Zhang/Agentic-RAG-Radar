# When Your Agent Opens the Chat App: Agent-Controlled Search over Raw Chat Logs Rivals Structured Memory

**arXiv:** [2608.12888](https://arxiv.org/abs/2608.12888) · **Published:** 2026-08-13 · **Category:** Retrieval & Tool Use · **Importance:** 4/5 · **AI confidence:** High

**Tags:** `memory` `sparse` `iterative search` `query rewrite` `adaptive stopping` `documents`

> **TL;DR.** ReFind leaves chat history as an append-only raw record and moves intelligence into question-time retrieval control: iterative lexical reformulation plus session-aware ranking, local context expansion, temporal filtering, and seen-session state. The important result is not “BM25 beats memory”; it is that a strong runtime interface can recover much of the value attributed to pre-built semantic memory structure.

## Problem

Most agent-memory systems decide how to compress or structure a conversation archive before the future question is known. Summaries, embeddings, trees, graphs, and memory cards can reduce online search cost, but they also make an irreversible bet about which details and relations will matter later.

ReFind asks the opposite systems question: **how far can we get by preserving the raw record and making runtime access smarter instead?**

## Core idea

Use a BM25 index over raw chat turns and expose a stateful retrieval interface specialized to conversational structure. The agent can reformulate keywords across rounds, use timestamps, exploit session-level evidence, expand around matched turns, skip sessions already inspected, and save only useful verbatim evidence for a separate answer stage.

The paper explicitly says no single control is novel; the contribution is the composition plus controlled evidence that this runtime design can substitute for much heavier pre-built memory structure on precise refinding tasks.

## Agent loop

`form keywords/time scope → search raw turns → inspect local/session context → save evidence → reformulate or narrow → skip seen sessions → stop when sufficient → answer from saved evidence`

## Retrieval design

The base index is turn-level BM25. Reciprocal Rank Fusion combines turn rank with aggregate session rank; each hit expands to nearby turns; optional timestamps filter the candidate space; and sessions returned in earlier rounds are excluded from later searches. The controller can stop early within a four-iteration budget.

This makes the interface state-dependent even though the stored history itself remains unchanged.

## Compared to what

Single-shot BM25-RAG, a **matched generic multi-round BM25 agent** without the chat-native controls, one-search control, structured memory systems such as HippoRAG 2 / GraphRAG / RAPTOR / STITCH / A-Mem, and matched dense/hybrid backend variants.

## Evidence

Across six MemoryAgentBench-derived tasks totaling about **2,800 questions**, with GPT-4o-mini matched across reused baselines, ReFind reports **58.2 mean accuracy**, versus **53.2** for HippoRAG 2 and **48.8** for single-shot BM25-RAG.

The more informative evidence is the matched LongMemEval-S/M control set with GPT-5-mini. The full interface reports **93.2±3.3 / 89.3±6.0**; the generic-agentic BM25 control gives **78.7±4.6 / 82.2±3.8**, and forcing one search gives **84.7±3.1 / 68.9±3.8**. Those comparisons separately weaken two simpler explanations: multi-round iteration alone is insufficient, and a good first query alone is also insufficient.

Two negatives matter. On EventQA, single-shot BM25-RAG is slightly better (**74.6 vs 74.1**), so not every chat-memory question needs agentic search. And in the matched backend ablation, dense/hybrid retrieval does not improve the mean, suggesting lexical matching is not the bottleneck in these tested subsets.

## Why it matters

This paper connects Agentic RAG and agent memory through a cleaner systems trade-off:

**precompute semantic structure for every update** versus **preserve raw data and spend adaptive computation only when a question arrives**.

The reusable insight is not that structure is bad. It is that memory papers need a stronger baseline: before crediting graph/tree/summary construction, compare against a controller with a good raw-data interface and native metadata controls.

It also creates a useful contrast with SIRA-like one-shot retrieval: when evidence is distributed across sessions and later queries can exploit newly exposed names/times, result-conditioned iteration has measurable value. “More rounds” is therefore neither inherently good nor inherently wasteful; its value depends on what information each round reveals that could not have been compiled before retrieval.

## Limitations / questions

- The substrate is text chat with turn, session, and timestamp metadata. Semantic abstraction, multimodal history, or globally diffuse questions may favor derived memory structure.
- The strongest GPT-5-mini ablations use small fixed LongMemEval subsets, including only 15 questions in M.
- Some baseline numbers are reused from prior benchmark papers rather than every system being rerun in one codebase.
- No-preprocessing is not no-cost: the paper reports roughly **2.5–2.6 searches and 5 LLM calls per query**, moving compute from memory construction to question time.

**Curator take:** **4/5**. Important because it provides a strong, factorized raw-memory baseline and shows where runtime control can substitute for offline structure. It is not a universal argument against semantic memory; the decisive next experiment is workload-factorized latency/accuracy/cost under the same storage fidelity and controller budget.
