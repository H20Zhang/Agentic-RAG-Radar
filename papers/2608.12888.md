# When Your Agent Opens the Chat App: Agent-Controlled Search over Raw Chat Logs Rivals Structured Memory

*Published 13 Aug 2026 · Retrieval & Tool Use · Importance 4/5 · Full-text reviewed · Confidence high*

[Paper](https://arxiv.org/abs/2608.12888)

> **TL;DR.** ReFind leaves chat history as an append-only raw record and moves intelligence into question-time retrieval control: lexical reformulation, session-aware ranking, local context expansion, temporal filtering, and seen-session state. The important result is not “BM25 beats memory”; it is that a strong runtime interface can substitute for some pre-built semantic memory structure on precise refinding tasks.

| 30-second verdict | |
|---|---|
| **Why this paper matters** | It gives structured memory a much stronger baseline: **raw-history fidelity + question-time control**. |
| **Strongest evidence** | On LongMemEval-S/M, full ReFind reaches **93.2 / 89.3**, versus **78.7 / 82.2** generic-agentic BM25 and **84.7 / 68.9** one-search. |
| **Biggest caveat** | EventQA slightly favors single-shot BM25, LongMemEval-M is small, and the design shifts several searches/LLM calls to query time. |

## Research question

How much semantic structure does an agent memory system actually need to precompute **before the future question is known**?

Most memory systems summarize, embed, cluster, graph, or compress history at write time. That can lower query-time work, but it also creates an irreversible information-selection decision before the eventual information need exists.

ReFind asks the opposite question: if the raw archive is preserved perfectly, can a sufficiently expressive runtime retrieval interface recover much of the same value only when the question arrives?

## Research delta

The paper's delta is a **chat-native, stateful lexical retrieval interface over the raw archive**.

The index itself is simple turn-level BM25. The system becomes stronger because the controller can use structure that already exists in the substrate:

- session-aware rank fusion;
- neighboring-turn expansion around hits;
- timestamp filtering;
- iterative keyword/time-scope reformulation;
- exclusion of sessions already inspected;
- explicit saving of verbatim evidence for a separate answer stage.

The authors do not claim each control is individually novel. The useful research claim is that this composition forms a strong **question-time alternative to mandatory pre-built semantic memory**.

## Mechanism

**Control flow.** `form keywords/time scope → search raw turns → inspect expanded session-local evidence → save useful fragments → reformulate/narrow → skip seen sessions → stop when sufficient → answer from saved evidence`

The design separates three objects that are often bundled in memory systems:

1. **Stored representation:** raw chronological turns remain intact.
2. **Retrieval interface:** search uses lexical ranking plus session/time/local structure.
3. **Controller:** the LLM decides how to adapt the next query after observing evidence.

That separation is what makes the matched ablations interesting.

## Evidence & attribution

| Claim | Evidence | Closest control | Assessment |
|---|---|---|---|
| Raw-history search can rival heavier structured memory | Mean **58.2** vs **53.2** for HippoRAG 2 and **48.8** for BM25-RAG across six tasks | Reused structured-memory baselines | **Useful system-level evidence**, but heterogeneous |
| Chat-native interface matters beyond generic iteration | **93.2 / 89.3** vs **78.7 / 82.2** on LongMemEval-S/M | Generic multi-round BM25 | **Strong matched support** |
| Result-conditioned iteration matters | **93.2 / 89.3** vs **84.7 / 68.9** | Forced one-search control | **Strong matched support** in these subsets |
| Agentic search is always needed | EventQA **74.1 ReFind vs 74.6 BM25-RAG** | Single-shot BM25 | **Rejected** |
| Dense/hybrid retrieval is necessary | Matched backend ablation does not improve mean | Dense/hybrid variants | **Not supported** on tested subsets |

The strongest evidence is not the leaderboard comparison against structured-memory systems. It is the pair of matched controls:

- generic multi-round BM25 asks whether **iteration alone** explains the gain;
- one-search asks whether a **good initial query** is sufficient.

Both are weaker than the full interface, suggesting that substrate-native controls and result-conditioned reformulation contribute independently.

The main systems caveat is displaced work. ReFind avoids LLM-based semantic memory construction, but the paper reports roughly **2.5–2.6 searches and 5 LLM calls per query**. This is a shift from write/update-time cost toward question-time cost, not a free removal of work.

## Where it fits

A useful placement lineage is:

`SIRA ↔ ReFind → LENS`

- **SIRA:** compile retrieval behavior before evidence by exposing corpus statistics.
- **ReFind:** defer intelligence until the question arrives and adapt from newly exposed session/time cues.
- **LENS:** defer even the **evidence boundaries** themselves until query time.

ReFind therefore sharpens a broader memory design question:

> **What information is stable enough to precompute, and what intelligence is better deferred until the future query reveals the actual need?**

It also provides a stronger baseline for semantic-memory work: a graph/tree/summary system should ideally beat a good raw-history controller after counting both construction/update and query-time cost.

## Open question

The decisive next experiment is **workload-factorized lifecycle accounting**:

> same raw history + same answer model + same accuracy target, comparing structured semantic memory and raw-history control across precise refinding, semantic abstraction, global summarization, and multimodal questions while measuring write/update cost, query latency, search calls, context, and storage.

That would reveal where precomputed memory structure genuinely buys something rather than merely moving computation across time.
