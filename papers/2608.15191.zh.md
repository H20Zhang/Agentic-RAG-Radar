# RAAC：把 Search Progress 变成可观察的 Control State

**中文** | [English](2608.15191.md) · [返回首页](../README.md) · [Research Library](../library/README.md)

[Paper](https://arxiv.org/abs/2608.15191) · **Importance: 4/5**

> **Research delta.** RAAC 不把“继续搜还是停”完全交给模型隐式判断，而是显式维护 coverage、document novelty、query diversity 与 drift 等 progress signals，用它们驱动 `continue / redirect / stop`。

## Problem

Deep-research agent 容易在 evidence 已经饱和后继续 search，重复访问相似文档或在越来越窄的 query neighborhood 里循环。只看 final answer 无法告诉我们 agent 是因为信息不足继续搜，还是已经 stagnate。

## Mechanism

`search → update progress signals → continue | stop | trigger critical re-thinker → substantially different query → search again`

RAAC 是 overlay controller：它不需要把底层 search agent 完全重写，而是根据显式 progress state 决定下一步。

## Closest comparison

论文把 RAAC 覆盖到多种已有 deep-research agent 上，最有价值的比较是**同一个 underlying agent 加/不加 RAAC**。这比跨 agent architecture leaderboard 更接近控制 controller effect。

但 RAAC 的 critical re-thinker 与 controller 自己也消耗 LLM compute，因此“search calls 减少”不是 matched total-cost comparison。

## Decisive evidence

BrowseComp-Plus 上，论文报告跨测试 agent 平均：

- search calls 减少约 **14 次**；
- accuracy 平均提升约 **3 points**，部分 setting 更高。

同时效果并不完全一致：有些 cell search 反而增多，或 recall/accuracy 没有同步改善。这个 heterogeneity 应保留在结论里。

## What remains unproven

下一步最关键的是把：

`controller/re-thinker calls + retrieval calls + inspected tokens + latency`

放进一个 matched budget，而不是只按 search-call count 比效率。

另外，当前 progress signals 是否能跨 source type、长时程任务与不同 search backend transfer，也需要验证。

## Field-map consequence

RAAC 把一条过去常隐式存在的 state 显式化：

`retrieval history → observable progress state → control decision`

这说明 iterative search 的 primitive 不是 round count，而是**信息增益/进展是否可被 controller 观察并利用**。
