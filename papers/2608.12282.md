# VAKRA: Evaluating Multi-Hop Reasoning Across APIs and Retrieval Under Tool-Use Policies

*Published 12 Aug 2026 · Evaluation & Analysis · Importance 4/5 · Full-text reviewed · Confidence high*

[Paper](https://arxiv.org/abs/2608.12282) · [Code](https://github.com/IBM/vakra)

> **TL;DR.** VAKRA is an executable benchmark for mixed-source agent trajectories: API calls, document retrieval, entity grounding, multi-hop reasoning, and natural-language tool policies must remain coherent in one run. Its strongest contribution is a **failure map for cross-source composition**, not a new agent architecture.

| 30-second verdict | |
|---|---|
| **Why this paper matters** | It evaluates the kind of heterogeneous information path real research/enterprise agents claim to execute. |
| **Strongest evidence** | The best model drops from **70.4%** on single-hop endpoint tasks to roughly **50–51%** on compositional APIs; trace analysis points to entity/cross-source grounding failures. |

## Research question

Can an agent maintain a coherent identity/evidence chain when a task requires **both structured API interaction and unstructured document retrieval under policy constraints**?

This is different from being good at API calling and document QA separately. Cross-source tasks introduce additional failure modes: the same entity must be resolved across sources, tool policies can change which actions are legal, and evidence from one source may determine what should be queried in another.

## Research delta

VAKRA's delta is benchmark design around **executable mixed-source trajectories**.

The environment provides more than 8,000 APIs across 62 domains, document retrieval, compositional tasks, and natural-language tool-use policies. Predicted tool calls can be re-executed, so evaluation does not require one canonical trace.

The authors intentionally hold the agent scaffold comparatively fixed with a ReAct harness. This is important to the interpretation: VAKRA is primarily measuring model capability under a common interface rather than claiming that its scaffold is the best controller.

The useful new evaluation object is therefore:

`source selection × entity grounding × executable tool use × document evidence × policy compliance × multi-hop composition`

inside one trajectory.

## Mechanism

**Control flow.** `interpret task/policy → choose API or document retrieval → observe structured/unstructured evidence → resolve entities and compose sources → continue, abstain, or answer`

The benchmark's information path contains several separable stages:

1. choose the relevant source/tool;
2. construct a valid API/retrieval action;
3. execute and observe evidence;
4. maintain entity identity across source boundaries;
5. integrate evidence under policy constraints;
6. know when the available sources do not justify an answer.

Because tool calls are executable, some errors can be located before final answer synthesis rather than hidden inside a single accuracy number.

## Evidence & attribution

| Claim | Evidence | Closest control | Assessment |
|---|---|---|---|
| Cross-source composition is materially harder than endpoint use | **70.4%** on single-hop endpoint tasks vs ~**50–51%** on compositional APIs for the best model | Same benchmark/harness family | **Strong diagnostic signal** |
| Policy-constrained unanswerable cases remain difficult | Some reported settings fall to **2.4%** | Same executable environment | **Strong evidence of a hard boundary** |
| Entity/cross-source grounding is a major failure surface | Trace analysis concentrates many errors there | Executable trajectory inspection | **Useful diagnostic evidence** |
| ReAct is the right controller | Harness is deliberately fixed rather than compared | No controller ablation | **Not evaluated** |
| A specific memory/retrieval intervention fixes the problem | Benchmark reports failures, not causal repair experiments | — | **Open** |

The fixed harness is both a strength and a limitation. It reduces one source of system variation when comparing models, but it also means benchmark failures cannot be attributed to the absence of a particular planning or memory mechanism.

A second attribution issue is stage coupling. Entity resolution, source selection, policy interpretation, retrieval, and synthesis can all fail in the same trajectory. VAKRA locates the general region of failure more cleanly than final-answer benchmarks, but counterfactual interventions are still needed to identify which single decision caused the downstream error.

## Where it fits

VAKRA belongs at the end of the radar's evaluation chain:

`evidence exists? → backend exposes it? → agent can inspect it? → source state is correct? → controller chooses well? → identity/evidence stays coherent across sources?`

Earlier papers isolate different points:

- **Training Protocols:** can the external environment support the target answer at all?
- **Pi-Serini:** is the backend ranking/depth being exposed fairly?
- **SGR-Bench:** is the external source in the correct retrieval state?
- **Is Grep All You Need?:** does the harness/delivery path change the conclusion?
- **VAKRA:** can the full trajectory preserve identity and grounding while crossing APIs and documents?

That makes VAKRA useful even without a new method: it expands what a credible “agentic retrieval” evaluation must keep coherent.

## Open question

The decisive follow-up is an **intervention benchmark on the same VAKRA tasks**:

> hold the model, tools, and total budget fixed; counterfactually repair source selection, entity resolution, retrieved evidence, or policy interpretation one at a time, then measure whether the remainder of the trajectory recovers.

That would turn VAKRA from a strong failure diagnosis into a causal map of which controller capability deserves research effort next.
