# VAKRA: Evaluating Multi-Hop Reasoning Across APIs and Retrieval Under Tool-Use Policies

> **TL;DR.** VAKRA evaluates agents in an executable mixed-source environment where API calls, document retrieval, multi-hop reasoning, and natural-language tool-use policies must work together; its strongest result is a failure map, not a new agent architecture.

## Problem

API-use benchmarks and document-RAG benchmarks usually isolate capabilities that production agents must combine. An enterprise task may require resolving an entity in one source, calling an API, retrieving supporting documentation, obeying a natural-language policy, and knowing when the evidence does not permit an answer.

If those pieces are evaluated separately, a system can look competent while still failing the cross-source trajectory.

## Core idea

VAKRA builds an executable benchmark around more than 8,000 APIs spanning 62 domains, paired with document retrieval and increasingly compositional tasks. Predicted tool calls can be re-executed, allowing multiple valid paths rather than requiring one canonical trace.

The authors deliberately use a **fixed ReAct harness** across models. That choice is important: VAKRA is primarily testing model capability under one agent interface, not claiming that ReAct is the best architecture.

## Agent loop

`interpret task + policy → choose API or document retrieval → observe evidence → resolve/ground across sources → continue, abstain, or answer`

## Retrieval design

Retrieval is part of the evaluated policy rather than a fixed context-building stage. In the multi-source setting, the model has to decide which information source to use and integrate unstructured document evidence with structured API results.

That makes the benchmark relevant to Agentic RAG even though a large fraction of the environment is API-centric: the information-acquisition decision spans heterogeneous tools and retrieval sources.

## Compared to what

The nearest comparison is not another RAG architecture. It is benchmark design: API-only tool-use suites, document-only RAG QA, or agent evaluations that score final answers without executable trajectory checks.

Using the same harness across models helps isolate capability differences, but it also means the benchmark does **not** answer which planner, memory system, or retrieval controller would solve the observed failures.

## Evidence

The paper reports that the strongest evaluated model reaches **70.4%** on single-hop endpoint-style tasks but only roughly **50–51%** on compositional API tasks; performance drops further with reasoning depth, and some policy-constrained unanswerable settings fall as low as **2.4%**.

The more important result is the trace analysis: failures concentrate around language-mediated reasoning such as **entity disambiguation and cross-source grounding**, rather than basic API invocation mechanics alone.

## Why it matters

This is a better stress test for the claim that an agent can do “enterprise research.” The hard part is not merely choosing a valid function name or retrieving a relevant chunk; it is maintaining a coherent identity/evidence chain across structured and unstructured sources under constraints.

For the radar, VAKRA adds a missing evaluation axis: **cross-source executable grounding**.

## Limitations / questions

- Because the harness is fixed, VAKRA is a model-capability benchmark more than a controller comparison; poor performance does not identify the best architectural remedy.
- The environment is more controlled than the open web, where source freshness, adversarial content, and retrieval noise add another layer of failure.
- Entity grounding, source selection, policy interpretation, retrieval, and synthesis can fail in the same trajectory. Intervention-style evaluation is still needed to isolate which control decision caused the final error.
- A decisive next step would compare several agent controllers on the same VAKRA environment while holding model and tool budget fixed.

**Curator take:** **4/5**. Important because executable API+retrieval composition is closer to real agent workloads than isolated QA/tool-call scores, and because the trace analysis points to a concrete failure boundary. It is not evidence for a new agent method by itself.
