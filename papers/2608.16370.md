# What Does Context Compression Cost an Agent? Interaction Costs Unrevealed by Task-Completion Metrics

**arXiv:** [2608.16370](https://arxiv.org/abs/2608.16370) · **Published:** 2026-08-17 · **Category:** Evaluation & Analysis · **Importance:** 4/5 · **AI confidence:** High

**Tags:** `memory` `iterative search` `general`

> **TL;DR.** Context compression can leave task completion statistically unchanged while forcing an agent to spend much more of its interaction budget re-querying external state. Oracle restoration of the dropped queryable state removes most of the extra retrieval, so completion-only evaluation can hide a real **reacquisition tax**.

## Problem

Context-management work is often evaluated by final task completion plus prompt/token reduction. For an agent with tools, that projection can be misleading: state removed from the prompt may simply be fetched again from the environment.

The hidden question is **where the saved context cost goes**.

## Core idea

Use a fixed 24-turn tool-use horizon and record a three-part outcome: task completion, retrieval calls used to reacquire state, and execution calls used to do task work.

The experiment varies compression severity/operator and uses oracle interventions that inject exact dropped state back into the compressed context. It separates externally queryable task state (`D`) from history-dependent state (`R`).

## Agent loop

`compression drops execution state → agent encounters missing information → re-query external state → continue task → repeated loss can trigger more reacquisition`

The oracle branch restores dropped state directly and tests whether the extra retrieval disappears.

## Retrieval design

This is an evaluation paper, not a new retriever. Retrieval is measured as **compensatory state reacquisition** under otherwise controlled context-management conditions.

That distinction matters for Agentic RAG because a context optimization can look efficient in tokens while making the retrieval policy appear unnecessarily active.

## Compared to what

Full context, sliding-window compression, fact-preserving extractive summary at the same compression ratio, oracle restoration of dropped queryable/history-dependent state, and ALFWorld as an external boundary condition.

## Evidence

At the prespecified `5×` comparison, retrieval increases in all six model-regime cells and **five of six** remain significant after Holm correction, while completion changes are not significant in any cell.

GPT-5.5 High is the sharpest example: completion changes **80% → 85% (p=1.0)** while retrieval rises **21.0 → 63.9 calls (p=.002)**. In DeepSeek High, restoring dropped queryable `D` state reduces tool calls **72.9 → 35.8** and recovers most of the completion gap.

The boundary condition is equally important: in ALFWorld, the same sliding compression produces **no retrieval surge**. The effect is not intrinsic to shortening context; it appears when execution-relevant state becomes unavailable and must be reacquired.

## Why it matters

This paper adds a missing resource axis to Agentic RAG evaluation: **state retention and retrieval effort are coupled**.

A system can report fewer context tokens without actually reducing end-to-end work. If the agent can re-fetch the dropped state, success may stay flat while tool traffic rises; if it cannot, completion may eventually fall. Completion therefore cannot tell us whether a context policy is actually efficient.

This also reframes “agent state.” The important property is not only how much state is stored, but whether dropped state is **recoverable, at what interaction cost, and within what horizon**.

## Limitations / questions

- The main environment is bounded and synthetic-adjacent with a fixed 24-turn horizon; ALFWorld is a boundary probe rather than a broad external validation.
- Three models show materially different translation from missing state to completion loss.
- Retrieval-call count is a tool-level interaction metric, not a full latency/monetary-cost model.
- The paper diagnoses a failure mode; it does not propose a general state-retention or retrieval-control policy.

**Curator take:** **4/5**. Important because the oracle intervention causally links dropped queryable state to extra retrieval and exposes a metric blind spot. The next step is production-like replay where context compression, caching, retrieval latency, and monetary cost are measured jointly.
