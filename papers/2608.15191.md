# When Deep Research Agents Stagnate: Enhancing Reasoning with Retrieval-Aware Agent Control

**arXiv:** [2608.15191](https://arxiv.org/abs/2608.15191) · **Published:** 2026-08-15 · **Category:** Iterative Reasoning & Verification · **Importance:** 4/5 · **AI confidence:** High

**Tags:** `iterative search` `adaptive stopping` `query rewrite` `evidence verification` `web research`

> **TL;DR.** RAAC treats deep-research stagnation as a trajectory-control problem: retrieval-aware progress signals summarize what has been covered and whether exploration is still novel, then an overlay controller decides to continue, redirect search, or stop. The matched same-agent comparisons are useful, but fewer search calls do not automatically mean lower total compute because the controller and re-thinker add LLM work.

## Problem

Deep Research Agents often keep searching after useful recall or answer quality has saturated. Across the seven evaluated systems, later rounds increasingly revisit previously seen documents while newly retrieved relevant documents decline.

The failure is not simply “too many steps.” It is **poor progress observability**: the agent does not explicitly know which criteria are satisfied, whether the last query explored a new region, or whether it should redirect rather than continue.

## Core idea

RAAC computes four unsupervised trajectory signals:

- criteria coverage over the information requirements;
- novelty of the current retrieved document set;
- diversity from the previous query;
- similarity to the original question as an anti-drift guardrail.

A controller then chooses `continue`, `intervene`, or `stop`. `Intervene` invokes a critical re-thinker that diagnoses why the trajectory is stale and generates a substantially different query.

## Agent loop

`search/reason → update coverage + novelty + diversity + alignment → continue | intervene | stop → redirected query if needed → retrieve → repeat or answer`

## Retrieval design

RAAC sits above the existing DRA instead of replacing its retriever. Within each dataset, the evaluated agents use the same retrieval pipeline and receive top-5 results per search.

This is a cleaner control point than comparing two end-to-end agents, because the same underlying DRA can be evaluated with and without the controller.

## Compared to what

Seven DRA families with and without RAAC, spanning ReAct-style, instruction/RL-trained, outline-guided, and report-writing workflows; plus prior adaptive retrieval controllers that use narrower trigger or stopping signals.

## Evidence

The analysis first shows the stagnation pattern directly: intermediate recall/accuracy often reaches a plateau while agents keep issuing searches and increasingly revisit seen documents.

On BrowseComp-Plus, the paper reports that RAAC reduces search calls by **14 on average** across the evaluated DRAs and improves accuracy by about **3 points on average**, with gains up to **10 points**. Several same-agent rows improve both recall and accuracy while using fewer searches.

The negative cells matter. CPM-Report uses more BrowseComp-Plus search calls with RAAC; some NeuCLIR/LegalSearch rows also increase calls or lose recall. The result is therefore **broad but not universal trajectory improvement**, not a theorem that the overlay always saves work.

## Why it matters

The reusable idea is that long search trajectories need an explicit notion of **progress**, not merely history. This sharpens the state question already raised by sufficiency/gap methods: a controller should know not only what evidence it has, but whether its information-acquisition process is still producing new value.

RAAC also raises the systems bar for adaptive stopping papers. Nominal search calls are not enough: the overlay adds coverage updates, controller decisions, and sometimes a critical re-thinker. A credible efficiency claim must count those model calls too.

## Limitations / questions

- Claude Sonnet 4.5 powers the coverage updater, controller, and critical re-thinker, so search-call reduction is not equivalent to total-compute or latency reduction.
- BrowseComp-Plus provides explicit criteria, while NeuCLIR and LegalSearch require LLM-generated/updated criteria; controller observability is not identical across datasets.
- `Intervene` bundles diagnosis, extra model compute, and query generation, so the gain is not isolated to the four signals.
- Effects are heterogeneous across agents/datasets, including cells with more searches or lower recall.

**Curator take:** **4/5**. Important because it turns “stagnation” into a measurable control problem and evaluates the overlay on the same underlying agents. The decisive follow-up is matched **total** controller/retrieval cost with a simpler stopping-only baseline and an intervention that separates signal quality from extra re-thinking compute.
