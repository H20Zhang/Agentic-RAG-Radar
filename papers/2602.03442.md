## Problem

Most RAG systems either retrieve once with a fixed algorithm or wrap a model around a hand-designed retrieval workflow. As models become better at tool use and test-time reasoning, that fixed workflow can become the bottleneck.

## Core idea

Expose retrieval at multiple granularities as direct model actions. Keyword and semantic search discover candidates; chunk read lets the model inspect evidence more precisely. The agent chooses among these interfaces rather than following a hard-coded retrieval recipe.

## Agent loop

`Reason → choose keyword/semantic search → inspect → chunk read → refine search or answer`

## Retrieval design

A hierarchical interface separates broad candidate discovery from fine-grained reading. The model controls the transition between operations, so retrieval becomes an interaction protocol rather than one backend call.

## Compared to what

Single-shot RAG, fixed retriever pipelines, and iterative RAG where the workflow is predefined by the system designer.

## Evidence

The paper reports strong open-domain and multi-hop QA performance, studies model/test-time-compute scaling, and reports comparable or lower retrieved-token budgets in evaluated settings. The radar has not yet re-checked the complete tables and budget definitions, so specific superiority claims remain provisional.

## Why it matters

A-RAG is a clean design anchor because it moves complexity from **workflow code** into **retrieval interface design**. If frontier models keep improving at sequential tool use, a small well-designed operation space may scale better than adding more hard-coded RAG stages.

It also creates a clearer systems question: **what should the retrieval API expose to the model?** That question now recurs in READ and DocNavRAG.

## Limitations / questions

- How much of the gain comes from the operation hierarchy versus larger test-time interaction budgets?
- How sensitive is the interface to the base model's tool-use competence?
- Is keyword + semantic + read close to a minimal sufficient operation set, or task-specific?
- How does the same interface compare against strong non-agentic orchestration using identical retrieval primitives?

**Curator take:** **4/5**. Strong as an abstraction/design anchor; exact empirical strength should be upgraded after a full-paper budget and ablation audit.
