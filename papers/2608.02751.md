# Search, Inspect, Fetch: Exploiting Boolean Retrieval for Deep-Research Agents

**arXiv:** [2608.02751](https://arxiv.org/abs/2608.02751) · **Published:** 2026-08-03 · **Category:** Retrieval & Tool Use · **Importance:** 4/5 · **AI confidence:** High

**Code:** [ielab/skim-search-agent](https://github.com/ielab/skim-search-agent)

**Tags:** `documents` `structured retrieval` `hybrid` `iterative search` `tool selection` `web research`

> **TL;DR.** SIEVE decomposes the agent-facing retrieval interface into four independently controllable decisions: **which sources are admissible, how they are ranked, what structure is visible before reading, and which section is fetched**. That factorization is more important than the Boolean-query syntax itself.


## Problem

Most deep-research agents use a `search → visit whole page` loop. That interface forces several different decisions into one path: relevance ranking chooses candidates, a small snippet helps the agent decide what to open, and opening then dumps a whole page into context. Native source structure—title, headings, sections, dates, fields—may remain visible to the model but is not necessarily **actionable**.

The systems question is therefore not just whether a better ranker finds the right page. It is whether the agent can express **eligibility constraints**, inspect source structure before paying the reading cost, and fetch only the evidence-bearing component.

## Core idea

SIEVE implements `search → inspect → fetch` over structured documents.

Search uses a fielded Boolean Query Language (BQL) to define an eligible set through AND/OR/NOT, field constraints, phrases, wildcards, and ranges. A separate ranker then orders only that admitted set. Result cards expose titles, headings, and short query-focused snippets. The agent finally fetches one named section or field rather than visiting the entire page.

## Agent loop

`formulate BQL → select eligible sources → rank → inspect result cards → fetch named section → update evidence/constraints → repeat or answer`

A zero-result query triggers a lexical fallback over the full collection, so exact filtering is not the only recovery path.

## Retrieval design

The most useful design decision is **selection ≠ ranking ≠ inspection ≠ reading**.

- **Selection:** BQL decides which sources are allowed into the candidate set.
- **Ranking:** BM25, dense retrieval, or fusion orders that set.
- **Inspection:** compact cards expose source structure without paying full-page context cost.
- **Fetch:** a named section becomes the read target.

This is more causal than comparing one complete RAG stack to another because several controls hold neighboring variables fixed. The paired flat/structured collections preserve emitted text while changing whether structure is addressable. Search–Fetch keeps iterative search, ranker, result depth, and section-level reading while removing BQL filtering.

## Compared to what

The closest baseline is **iterative Search–Fetch**, not ordinary one-shot RAG. Search–Visit changes both reading granularity and candidate-selection behavior relative to SIEVE, so attributing the full system difference to Boolean retrieval would be too broad.

DCI and RISE are also important design neighbors. DCI exposes raw high-resolution corpus operations; RISE bounds that interaction for scale. SIEVE instead preserves document structure through a more constrained interface, keeping ranking modular while making fields and sections first-class agent actions.

## Evidence

Across HotpotQA, MuSiQue, and BrowseComp-Plus-Structured, the default BM25+Dense SIEVE configuration is reported to exceed the most accurate conventional Search–Visit configuration on each collection while using **20.7–50.6% fewer distinct tokens**.

The more informative evidence is the matched control: BQL-filtered SIEVE improves over Search–Fetch across all nine ranker–collection pairs in the reported study. Retriever substitutions and three agent backbones also test whether the interface result depends on one ranker/model combination.

The paper separately reports both distinct-context tokens and step-summed tokens, reducing the risk that the efficiency claim is only an accounting artifact.

## Why it matters

SIEVE makes the retrieval interface **factorable**. For agent systems, “the retriever” is too coarse an experimental variable. Candidate admissibility, ranking, pre-read observation, and reading granularity can each change behavior and resource use.

That suggests a stronger future evaluation pattern: keep the answer model and surrounding harness fixed, then independently toggle exact candidate constraints, ranker, result-card information, and read granularity. The system becomes easier to reason about because each control point has a separate causal role.

## Limitations / questions

- BrowseComp-Plus-Structured uses model-proposed section boundaries, so some of the structure is constructed rather than native.
- BQL zero-result fallback is frequent, which means recovery from over-constraint is part of the effective method and should not be ignored when comparing “Boolean retrieval” alone.
- The tested collections still abstract away much of live-web volatility, malformed markup, access restrictions, and dynamic content.
- How much of the gain remains if strong structured result cards and section fetch are kept but candidate eligibility is learned or semantic rather than Boolean?

**Curator take:** **4/5**. Important because it decomposes the retrieval interface into independently testable decisions and backs that decomposition with unusually useful matched controls. The transferable idea is broader than BQL: **preserve structure and separate admissibility, ordering, inspection, and reading.**
