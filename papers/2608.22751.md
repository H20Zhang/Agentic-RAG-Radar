# Risk-Aware Reranking for Agentic Tool Retrieval

*Published 24 Aug 2026 · Retrieval & Tool Use · Importance 4/5 · Full-text reviewed · Confidence medium*

[Paper](https://arxiv.org/abs/2608.22751) · [Code](https://github.com/qli447/risk-aware-tool-retrieval-release) · [CIKM](https://doi.org/10.1145/3799682.3840706)

> **TL;DR.** This paper makes the retrieved tool shortlist an explicit pre-execution exposure surface. The cleanest ablation adds a learned risk head to the same frozen representations: RVR@5 falls from 0.188 to 0.138 while NDCG@5 moves from 0.558 to 0.551. That is evidence for a tunable labeled exposure–relevance tradeoff—not evidence that agents execute tools more safely.

| 30-second verdict | |
|---|---|
| **Why this paper matters** | Tool retrieval selects executable options, so candidate exposure deserves its own objective and audit. |
| **Strongest evidence** | Same relevance head and frozen encoder, with only the learned risk head added: RVR@5 **0.188 → 0.138**. |

## Research question

Can a tool retriever preserve useful candidates while reducing unnecessary exposure to higher-risk executable actions before the agent acts?

## Research delta

The smallest delta is **risk-aware tool exposure at retrieval time**. Risk and relevance are scored separately, then combined with an inference-time coefficient. An audited deployment can add deterministic caps over risk and permission metadata.

## Mechanism

**Control flow.** `query → score relevance and tool-level risk → tune λ → optional graph/rules → expose top-k → agent chooses`

The learned core predicts tool-level risk from descriptions. It does not reason about call arguments, user permissions, or runtime environment. The rule mode is a different deployment condition: it directly consumes audited labels and permission categories.

## Evidence & attribution

| Claim | Evidence | Closest control | Assessment |
|---|---|---|---|
| Learned risk scoring lowers labeled exposure | UltraTool NDCG/RVR/SRR **0.558/0.188/0.097 → 0.551/0.138/0.063** | Same frozen ToolRet-BGE and trained relevance head | Strong component evidence |
| Hard filtering is conservative | RVR/SRR fall to **0.073/0.019** | Same package plus audited rules | Supported, but metadata-dependent |
| Needed risky tools remain available | NeedRisk-Hit **0.660 → 0.397** across controls | Same benchmark | **Not supported** |
| The package makes agents safer | Candidate analysis only; no execution outcomes | None | **Unproven** |

The main reranker table is not the causal center: general rerankers see ToolRet's top-100 while the end-to-end method scores the full pool. The graph also does not improve the risk metric in the component ablation.

## Where it fits

`capability retrieval → candidate-action exposure → execution guardrails`

This is a new early signal under Retrieval & Tool Use. It complements ToolScout's candidate-coverage audit, but coverage and exposure risk are different failure surfaces.

## Open question

Execute matched tasks while independently varying candidate set, risk objective, rule metadata, and downstream executor under equal retrieval latency, scoring cost, calls, and permissions. Measure both task success and realized harm—not only labeled top-k composition.
