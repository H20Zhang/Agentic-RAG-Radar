# RetrievalRouter: Joint Modality and Architecture Selection for Document Retrieval

*Published 26 Aug 2026 · Learning & Optimization · Importance 4/5 · Full-text reviewed · Confidence medium*

[Paper](https://arxiv.org/abs/2608.25625) · [Code](https://github.com/emrekuruu/retrieval-router)

> **TL;DR.** RetrievalRouter learns from query text alone which sparse/dense/reranked text-or-multimodal pipeline to run. It improves the online accuracy–latency frontier over static and adapted hard-label routing controls, but the comparison does not price the lifecycle cost of maintaining every underlying index.

## Research question

When one corpus can be searched by sparse, dense, reranked, text, and multimodal pipelines with asymmetric failures, should one pipeline be fixed globally or selected per query?

## Research delta

The useful delta is not simply “router beats static retrieval.” It is:

`query → query-only policy → modality × architecture choice → one retrieval pipeline`

The action space spans five deployable arms—BM25, text dense, text rerank, multimodal dense, and multimodal rerank—while the training target uses each arm's per-query quality/latency reward rather than an arbitrary hard winner.

## Mechanism

A frozen Qwen3-0.6B base with LoRA produces a query representation and a linear head outputs probabilities over the five routing arms. For training, all arms are run offline to build a reward vector combining nDCG@5 and normalized latency. A low-temperature softmax converts that vector into a soft target, preserving ties and near-ties rather than forcing one hard class.

At inference, the router runs once, adds about 15 ms overhead, and only the selected retrieval pipeline executes.

## Evidence & attribution

| Claim | Evidence | Closest control | Assessment |
|---|---|---|---|
| Query-conditioned routing improves the static frontier | `λ=.1`: **0.755 / .666 s** vs ML **0.737 / 8.283 s** | Best static pipeline | Strong online result |
| Soft-target routing improves prior adaptive strategy selection | `λ=.1`: **0.755 / .666 s** vs **0.715 / .476 s** | Adapted Arabzadeh hard-label router | Better quality, slower |
| Latency-oriented routing may dominate prior adaptive routing | `λ=.7`: **0.630 / .148 s** vs **0.624 / .171 s** | Same adaptive baseline | Numerical only; not significant at paper threshold |
| Large routing headroom remains | Oracle reaches about **0.90 nDCG@5** | Per-query seven-pipeline oracle | Upper bound, not deployable |

The paper measures end-to-end per-query latency on one H100 including routing, embedding generation, and vector search. That is a good online denominator. It is not a lifecycle denominator: the system still stores and maintains all retrieval substrates needed for future routing decisions.

## Where it fits

`pre-retrieval adaptivity → query-conditioned pipeline routing → evidence acquisition`

This is an `early_signal`. It strengthens the case that “which retriever?” is itself a policy decision, but it does not establish that multi-pipeline routing is cheaper once storage, build, update, and cache pressure are charged.

## Open question

Hold corpus, answer model, recall target, and traffic fixed, then compare one adaptive multi-index router with the best single-index system and a cascade while charging **index build + update + storage + cache residency + router training + online latency**. That experiment would tell whether routing moves cost or removes it.
